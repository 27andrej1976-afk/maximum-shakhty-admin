## Готовые изменения

Исполняемые изменения в этом PR затрагивают только три существующих workflow main: gorod-apk.yml, gorod-v091-icon-apk.yml, gorod-yandex-beta.yml. APK-копии Actions: 14 дней; браузерный отчёт Яндекс-беты: 7 дней. Проверка Android сохраняет прежние 7 дней.

В этих трёх workflow из push.paths исключён только собственный YAML-файл: изменение срока хранения само по себе больше не запускает сборку и публикацию APK. Пути исходников сохранены, ручной workflow_dispatch сохранён. При будущих изменениях самой логики workflow проверку можно запустить вручную после согласования сборки. Остальные условия, шаги, разрешения, приложения и публикации не меняются.

В branch-patches/ подготовлены отдельные точные unified diff для 12 workflow экспериментальных веток. Они НЕ добавлены в .github/workflows основной ветки и НЕ применены к рабочим веткам. Это неисполняемые предложения, созданные из текущих файлов соответствующих веток. Они вводят 7 дней для отчётов и 14 вместо 30 для APK PanFix. Файлы с уже установленными 7 днями не меняются. Перед применением проверить целевую ветку и blob SHA в таблице ниже; использовать git apply --check. Не применять пакетом: изменение YAML в старой ветке может автоматически запустить старый процесс, который публикует файлы в main. Сначала отдельно согласовать повторный запуск или убрать путь собственного YAML из push.paths аналогично основному PR.

## Сохранение установщиков и результатов

В main уже есть 10 APK в downloads-каталогах, размером от 26 853 до 615 508 байт. Для трёх меняемых workflow сохранены их существующие шаги публикации APK в gorod-control/downloads, gorod-control/direct-v09/downloads и gorod-control/yandex-v1/downloads. Артефакты Actions — дополнительные копии. Утверждённые установщики по действующим ссылкам остаются в репозитории; этот PR не меняет ни одного APK.

Отчёты сохраняются полностью семь дней; условия always/failure/success и состав файлов сохранены. Нужные контрольные результаты следует отдельно сохранять до истечения срока. Автоматической очистки по принципу «оставить последний» нет: она может уничтожить нужное сравнение. Старые артефакты этим PR не удаляются и не получают новые сроки задним числом. Для долгосрочного хранения утверждённых установщиков возможны Releases, но их создание/перенос требуют отдельного согласования и сейчас не выполняются.

## GitHub Pages — основной текущий объём

Динамический pages-build-deployment сохраняет пакет сайта размером около 5,26 МиБ на один день. Проверенный запуск 39214066548 успешно выполнил build/upload/deploy; это не Android-сборка. Успех сборщика данных 39208008594 также не подтверждает работоспособность всех будущих APK-загрузок.

Два сборщика данных имеют по четыре запуска в час по cron (в сумме до 192 плановых запусков в сутки; фактическое выполнение задерживается GitHub). Они фиксируют обновления в main; это порождает новые публикации Pages. В истории найдено 401 динамическое выполнение Pages. Не каждый cron обязательно создаёт коммит, и это не оценка ежедневного числа публикаций.

Pages уже использует минимальный срок в один день; его нельзя безопасно сократить retention-days ниже 1. Перевод публикации в собственный workflow с объединением ожидающих публикаций или уменьшение пакета сайта могут дать больший эффект, чем APK-политика. Но для этого надо проверить настройки Pages, все публичные пути, частоту обновления данных и публикацию бинарных установщиков. Такие изменения могут повлиять на работающие приложения и в этот PR не входят. Не сокращать частоту коммунальных предупреждений ради экономии без отдельного решения.

## Расходы и риск блокировки

Официальная документация GitHub указывает бесплатность Actions в публичных репозиториях на стандартных runners; maximum-shakhty-admin публичный. alisa-2 приватный, поэтому минуты могут расходовать включённый лимит. Во всех изученных пользовательских workflow используются ubuntu-latest, более дорогих larger runners не обнаружено.

Текущая документация: дополнительное shared storage — $0,25 за ГБ·месяц; Linux 2-core — $0,006 за минуту сверх включённого лимита. Иллюстрации, не счёт аккаунта: 1 дополнительный ГБ весь месяц — около $0,25; 1000 дополнительных Linux-минут — около $6. Раздел Billing необходим, чтобы установить конкретные платные SKU, применимость публичного хранения к уведомлению, потребление GitHub Packages и реальные начисления.

Без действующего способа оплаты исчерпание квоты может блокировать использование; при наличии способа оплаты перерасход зависит от бюджетов. Уведомление 100% не подтверждает ни автоматическое списание, ни остановку всех процессов. Может отказать именно upload-artifact, хотя проверки и компиляция ранее выполнялись. В PanFix артефакт нужен для передачи APK между build_test и publish, поэтому отказ upload/download сорвёт публикацию. В трёх основных APK-процессах upload-artifact расположен после публикации: неуспешный итог запуска может сочетаться с уже опубликованным APK; перед повтором всегда проверять шаги.

Хранение учитывается по времени (ГБ·часы). Сокращение сроков снижает будущий расход, но не отменяет уже накопленный; обновление показателя может занять 6–12 часов. Начало нового цикла 1 ноября взято из предоставленного уведомления; старые файлы сами по себе не исчезают в этот день. Изменение срока с 90 на 14 даёт до 84,4% сокращения времени хранения новых дубликатов APK; с 90 на 7 — до 92,2% новых отчётов при сопоставимом потоке. Это не обещание снижения всего аккаунтного расхода на тот же процент.

Практический контроль расходов: просмотреть Settings → Billing and licensing → Usage и Budgets and alerts, проверить именно жёсткую остановку использования при лимите, а не только уведомление. Бюджеты, платёжные методы и тарифы в этой работе не менялись. Cache имеет отдельную квоту (10 ГБ на репозиторий по текущей документации); Gradle cache и cache debug.keystore не приравниваются к APK-артефактам. Нельзя удалять debug.keystore ради очистки: смена подписи может нарушить установку обновлений.
