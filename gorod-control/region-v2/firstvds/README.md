# Изолированное размещение на имеющемся FirstVDS

Подготовка выполнена 12.11.2026 после явного разрешения Андрея открыть VNC-консоль сервера №18772218 и подготовить отдельное размещение «Дон под контролем», включая приватное хранение MAX-сессии. Прежний блокер разрешения снят. Действующий сервер использует Caddy, не Nginx. Его конфигурация и чужие проекты не менялись.

Код установлен из commit c7885c432c42de4fd29ac5ee3c20db13fe1351de; исправление прав кода/venv применено отдельно и проверено реальным запуском. Изолированные пути: `/opt/don-control`, `/etc/don-control`, `/var/lib/don-control`. Службы подготовлены, обе в конечном состоянии inactive. Постоянный MAX-сборщик, публичный HTTPS-маршрут и реальная лента не запущены. Сама сессия ещё не перенесена.

Пакет формируется `prepare_deploy.py --output <каталог>`. `install-prepared.sh <каталог пакета>` размещает код, venv и service units, но не запускает сервисы, не меняет reverse proxy и не переносит сессию. Он не перезаписывает неизвестный каталог и сохраняет имеющиеся feed/health/проверенную конфигурацию. Явный umask 0022 и права чтения/прохода на код/venv нужны при закрытом root-umask; private state/session всегда создаются с 0700.

Отдельный пользователь `don-control` обслуживает MAX/SQLite; `don-web` выдаёт только публичную ленту. Проверено: у don-web нет прохода в session. HTTP `/session/max-session.db` возвращает 404. Сессия не должна попадать в публичную папку, исходники, артефакты, журналы и публичные резервные копии сайта. Пакет SDK закреплён: `maxapi-python==2.4.1`; импорт WebClient на сервере успешен.

Локальный smoke check: временный старт don-public, HTTP 200 для страницы и /healthz; health сообщает feedAvailable=false и incidentPipelineVerified=false. Служба после проверки остановлена. Сборщик --check-config штатно отказывает disabled-реестру, не обращаясь к аккаунту. Это не успешный запуск карты аварий.

Файлы `nginx.location.conf` сохранены только как старый пример, к этому серверу их не применять. Для дальнейшего маршрута Caddy сначала прочитать актуальный блок нужного хоста, проверить совпадения и существующие catch-all; подготовить резервную копию. Проверить Caddy-конфигурацию его установленным бинарным файлом до штатного reload. Не менять корневые маршруты, не перезапускать сервер и не создавать платные ресурсы. Веб-сервис должен слушать только 127.0.0.1:8791.

Перед живым сборщиком нужны подтверждённые профильные источники, реальный территориальный каталог и обработка публикаций. Worker не должен обходить эти проверки. После подключения отдельно проверить: повторное чтение MAX; новый и сохранённый event/feed; отказ/возврат источника; перезапуск SQLite; восстановление/36 часов; отсутствие сессии/SQLite в HTTP; получение ленты Android. После Caddy reload проверить действующие проекты. Только затем готовить выпуск с постоянной подписью и реальными материалами RuStore.
